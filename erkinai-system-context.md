## 1. Продукт и концепция

**ErkinAI** — AI-операционная система самостоятельного бизнеса.
Позиционирование: не «аналитика» и не «отчёты», а второй мозг компании.

Формула продукта (повторяется в презентации, соблюдается везде в UI и в текстах ИИ):

> **Что происходит. Почему это важно. Что делать дальше.**

Триада действий системы: **Видит → Предупреждает → Подсказывает.**

Ключевой принцип: **не после проблемы, а раньше.** Ценность не в отчёте за вчера,
а в предупреждении о том, что ломается сейчас или сломается завтра.

Три столпа, вокруг которых строится вся аналитика:

| Столп | Что охватывает |
|---|---|
| **Деньги** | Выручка, расходы, потери |
| **Люди** | Нагрузка, эффективность, исполнение |
| **Процессы** | Задачи, узкие места, скорость |

Боли клиента, которые продукт закрывает: сотрудники ждут решений, задачи требуют
контроля, деньги теряются незаметно, владелец становится диспетчером.

## 2. Вертикализация

ErkinAI — продукт для любой сферы. Медицина (педиатрическая клиника, бывш. «Мама Доктор») —
первая вертикаль, а не единственная. Отсюда правило именования:

**В аналитическом слое (вьюхи, метрики, API дашборда) используются только
доменно-нейтральные термины. Отраслевые слова живут в словаре локализации.**

| Нейтрально | Медицина | Бьюти | Автосервис | Образование |
|---|---|---|---|---|
| `client` | пациент | клиент | клиент | ученик |
| `resource` | врач | мастер | пост / механик | преподаватель |
| `appointment` | приём | визит | заказ-наряд | занятие |
| `service` | услуга | услуга | работа | курс |
| `location` | филиал | салон | СТО | площадка |
| `staff` | администратор | администратор | приёмщик | менеджер |

Метрики делятся на два слоя:

- **Ядро** — есть в любой вертикали: выручка, средний чек, загрузка ресурсов,
  no-show, повторные обращения, конверсия воронки, новые vs вернувшиеся клиенты.
- **Отраслевые** — подключаются конфигом вертикали (для медицины: доля прививок,
  возрастные группы, повторные визиты по профилю).

**Механизм уже есть в CRM и его не нужно строить заново** (заполнено по коду):

- у организации есть поле `vertical` (проверено на проде: орг 1 → `"clinic"`);
- термины хранятся в `src/locales/glossary/<вертикаль>.json` — **12 словоформ**
  (6 падежей × 2 числа) плюс род, потому что русский склоняется и плоская замена
  слова ломает фразы («Карта клиент»);
- строки интерфейса — в `src/locales/ru/<модуль>.json`, подстановка через
  `useT()` / `tt()`;
- ⚠ род термина меняется между вертикалями (медсестра → ассистент), поэтому
  формулировки безличные: «Запись создана», а не «Пациент добавлен».

Вывод для дашборда: правило «нейтральные термины в слое данных, отраслевые в
словаре» совпадает с тем, что уже сделано. Метрики именовать `client`/`resource`,
подписи брать из глоссария.

`ВОПРОС РУКОВОДСТВУ:` подтвердить список вертикалей после медицины.

## 3. Роли и права

Дашборд **один**, срез данных и набор виджетов определяются ролью.

| Роль | Горизонт | Что видит | Область данных |
|---|---|---|---|
| **Администратор** | сегодня / неделя | операционка: записи на день, неявки, необработанные лиды, свободные слоты | свой `location` |
| **Управляющий** | неделя / месяц | эффективность: конверсия воронки, загрузка ресурсов, KPI сотрудников, отказы | свои `location` (может быть несколько) |
| **Владелец** | месяц / квартал | деньги и тренды: выручка, средний чек, деньги под риском, динамика, сравнение филиалов | все `location` |

**Критическое требование.** Роль ограничивает не только состав виджетов, но и
**строки данных**. Фильтрация по `location_id` / `role` выполняется **на бэкенде**,
в параметрах обращения к вьюхе. Отдавать полный набор и прятать на фронте — нельзя:
это не права доступа, а их имитация, данные видны в DevTools.

### Что уже есть (заполнено по коду 25.08.2026)

**Роли существуют, заводить не нужно.** В системе: `superadmin`, `admin`,
`doctor`, `nurse`, `receptionist`, `registrator`, `accountant`, `manager`,
`owner`. Соответствие ролям дашборда: Администратор → `admin`/`receptionist`,
Управляющий → `manager`, Владелец → `owner`.

⚠ Роль — это **только именованный набор permission-кодов**, который организация
настраивает сама. Проверять «если роль = владелец» нельзя: организация вправе
собрать роль иначе. Гейт всегда по праву (`can("reports.view")`). Для дашборда
это значит: **нужен свой permission-код** (например `dashboard.view` и
`dashboard.finance.view`), а не привязка к именам ролей.

**Да, один пользователь может иметь несколько ролей и филиалов.** Модель:
пользователь → `memberships[]` (по одному на организацию) → в каждом членстве
одна роль + список филиалов (`branches[]`, `UserBranchAccess`). Плюс личные
надбавки поверх роли: `grantCodes` / `denyCodes`. Активная организация и филиал
сессии приходят в `GET /api/auth/me/`.

⚠ **Требование «фильтрация на бэкенде» сегодня выполняется не полностью.**
Приёмы, брони, расписание и остатки бэк режет по филиалу; **задачи не режет
вовсе**, а часть агрегатов фильтруется на фронте. Для дашборда это придётся
закрыть на бэке — иначе владелец и администратор увидят одни и те же строки.

⚠ Суперпользователю обязателен `organizationId` в запросе, иначе 400.

## 4. Модель данных

Заполнено 25.08.2026 по контрактам API (не по схеме БД — она фронтенду не видна).

### 4.1 Client (пациент)

Поля: `id`, `organizationId`, `branch`, `fullName`, `phone`, `secondaryPhone`,
`birthDate`, `gender`, `address`, `notes`, **`source`** (источник привлечения —
есть), `photoUrl`, `inn`, `isBlacklisted` + `blacklistReason`, `isActive`,
`createdAt`, `updatedAt`, `family`.

⚠ **Отдельной сущности «ребёнок» нет.** Ребёнок — обычный пациент со своей
картой, возраст из `birthDate`. Связь с законным представителем выражена двумя
способами:

1. **Семья** (`Family`: `id`, `organizationId`, `branch`, `name`, `memberCount`) —
   карты объединяются в семью явным полем при заведении пациента;
2. **телефон родителя записан в карте ребёнка** — поэтому один номер
   соответствует многим картам (встречалось 11 карт на номер).

Для метрик это ключевая развилка: «повторные обращения» и «новые vs вернувшиеся»
можно считать **по карте** или **по семье** (`familyId` даёт агрегацию по
домохозяйству). В педиатрии это разные цифры: трое детей одной семьи — три
карты, но один плательщик.

⚠ **Дат первого и последнего обращения в карте нет** — таких полей API не
отдаёт. Считать по таблице приёмов.

### 4.2 Resource (врач)

Карточка сотрудника: ФИО, телефон, **специализации**, **привязка к филиалам**,
ставка и правила оплаты (оклад / процент / за смену), банковские реквизиты (за
отдельным правом), фото, участие в онлайн-записи, параметры предоплаты.
Связь с учётной записью — через `membership` (`userId` ↔ `authUserId`).

**График** — модуль расписания: смены по филиалам плюс исключения
`ScheduleExceptionKind = "day_off" | "vacation" | "extra" | "override"`.
То есть выходные и отпуска в модели **есть** — загрузку ресурса можно считать
честно, а не «делить на 8 часов».

**Стоимость приёма** живёт не у врача, а в услуге (см. 4.4); у врача — правила
его оплаты труда.

### 4.3 Appointment (приём)

Ключевая сущность для аналитики.

Поля: `id`, `organizationId`, `branchId`/`branchName`, `patient`, `scheduledAt`,
`endsAt`, `isNight`, `status`, `services[]` (услуга, исполнитель, количество,
`unitPrice`, `lineTotal`, скидка, расходники), `productLines[]` (товары внутри
приёма), `complaints` / `doctorComplaints` / `adminComment`, `totalAmount`,
`discountAmount`, `payableAmount`, `paidTotal`, `debt`, `paymentStatus`,
`paymentMethods[]`, `priceOverrides[]`, `hasMedicalConclusion`,
`createdById` / `updatedById`, `createdAt` / `updatedAt`.

⚠ Филиал приходит **объектом** `branch`, а не полем `branchId`.
⚠ У строки услуги может не быть `price` — деньги считать от `lineTotal`.

#### Статусы — реальный список (черновик в прежней версии файла был неверен)

**15 канонических кодов на двух независимых осях** (`config/appointmentStatuses.tsx`):

**Ось визита (`track: "visit"`):**
`scheduled` → `confirmed` → `arrived` → `in_progress` → `completed`,
ветки выхода `canceled` и `no_show`.

**Ось денег (`track: "money"`):**
`paid`, `paid_cashless`, `partially_paid`, `debt`, `discounted`, `free`,
`insurance`.

Отличия от чернового набора, которые ломают метрики, если их не учесть:

- начальный статус — **`scheduled`**, не `new`;
- **отмена одна: `canceled`**, деления `cancelled_by_client` /
  `cancelled_by_clinic` в системе **нет**. Есть текстовое поле `cancelReason`.
  ⇒ Метрику «кто отменил» сегодня посчитать нечем — либо разбирать текст
  (ненадёжно), либо просить бэк добавить признак инициатора;
- статус визита и статус оплаты — **разные оси**, а не одна цепочка.

⚠ **Канонической схемы переходов не существует ни в документации, ни в API.**
Проверялось: схему из бэка достать не удалось, допустимость перехода выясняется
кликом в UI. Практическое следствие: **автоперехода по факту оплаты нет**,
поэтому на проде подавляющее большинство приёмов остаётся в
`scheduled`/`confirmed` даже будучи оплаченными. Метрика «завершённые приёмы»
по статусу `completed` даст заниженную цифру — считать надо по оплате.

`ВОПРОС БЭКЕНДУ:` зафиксировать матрицу переходов и признак инициатора отмены.

### 4.4 Service (услуга)

Название, **цена**, **`durationMinutes`** (есть — загрузка ресурса считается),
категория (`doctor` / `nurse` / `lab` / `hardware`), видимость на витрине
онлайн-записи, состав расходников (товары, списываемые при оплате), связанные
товары, признак платности расходника.

### 4.5 Location (филиал)

Название, адрес, телефоны, расписание работы, собственный склад и остатки.
Организация 1→N филиалов. Рабочие сущности принадлежат филиалу, справочники —
организации.

### 4.6 Payment (оплата)

`method`: `cash` | `card` | `balance` | `bonus` | `insurance`.
`PaymentStatus`: `unpaid` | `partial` | `paid` | `discounted` | `refunded`.

Поля платежа: `amount`, `createdAt`, **`cashDate`** (дата, на которую деньги
попадают в кассу — для карты и страховой отличается от даты создания), для
страховой `insurerId` / `policyNumber`, для карты `cashlessMethodId` /
`cashlessMethodName` (Бакай POS, MBank и т. д. из справочника).

Сводка по приёму: `totalAmount`, `discountAmount`, `payableAmount`, `paidTotal`,
`refundedTotal`, `bonusPaid`, `debt` + список платежей.
**Частичные оплаты и возвраты поддержаны**; возврат — отдельная запись со
ссылкой на платёж, суммой и причиной. Возвраты проводятся сторно и в кассовые
агрегаты не входят.

Все суммы — **строки-decimal**, не числа.

### 4.7 Lead / Deal (воронка)

**В системе воронки нет.** Ни сущности лида, ни этапов, ни канбана по клиентам.

Что есть и на что это похоже:

- **Брони** — заявка с публичной витрины или из партнёрского API: приходит,
  подтверждается, материализуется в приём. Это готовая двухшаговая воронка
  «заявка → запись», по ней считается конверсия онлайн-записи;
- **Задачи** (`/tasks`) — канбан есть, но по внутренним задачам сотрудников,
  а не по клиентам.

`ВОПРОС РУКОВОДСТВУ:` решение amoCRM vs собственная реализация — не принято.
Замечание из прежней редакции остаётся в силе: если воронка уедет в amoCRM,
конверсию придётся тянуть по API, что ломает подход «всё считается вьюхами».

## 6. Бизнес-правила

> **Самый важный раздел файла.** Без явно зафиксированных правил дашборд посчитает
> цифры не так, как их считает руководство, и всё придётся переделывать.

Ниже по каждому вопросу — **как система считает сегодня** (факт из кода) и
**что осталось решить руководству**. Первое — не ответ на второе: сегодняшнее
поведение может руководство и не устраивать, но оно задаёт цену изменения.

### 6.1. Что попадает в выручку

**Сегодня:** «оплачено» = статус **`paid` или `discounted`**. Это правило
действует в реестрах, отчётах и в зачёте достижений. Считается **по строкам
услуг** среза (`lineTotal`), а не по полю суммы приёма. Товары внутри приёма
оплачиваются платежом приёма; самостоятельные продажи склада считаются отдельно.
Дата отнесения денег — **`cashDate` платежа**, а не дата приёма и не дата
создания платежа. Возвраты — сторно, в кассовые агрегаты не входят.

`ВОПРОС РУКОВОДСТВУ:` выручка по дате платежа (как сейчас) или по дате приёма?
Считать ли частично оплаченные (`partial`) и долги (`debt`)?

### 6.2. Что считается неявкой

**Сегодня:** `no_show` — **отдельный статус**, выставляется **вручную**.
Автоматического перевода по времени нет. Приём остаётся в истории и реестрах,
но не оплачен, поэтому в выручку не попадает. Отмена — другой статус
(`canceled`) с текстовой причиной; инициатор отмены не фиксируется (см. 4.3).

`ВОПРОС РУКОВОДСТВУ:` отмена за час до приёма — отмена или неявка?
Нужен ли автоперевод в `no_show` по концу дня (сейчас его нет, и статистика
неявок зависит от дисциплины регистратора)?

### 6.3. Что считается повторным визитом

**Сегодня:** **не реализовано.** Система не делит приёмы на первичный и
повторный и нигде это не считает. «Повторная запись» в интерфейсе — просто
быстрый способ создать приём тому же пациенту.

Считать придётся самим, и развилка не техническая, а смысловая: **по карте
или по семье**. Поле `familyId` позволяет и то и другое (см. 4.1).

`ВОПРОС РУКОВОДСТВУ:` любое второе обращение или в пределах N месяцев?
По карте пациента или по семье?

### 6.4. Как считается загрузка ресурса

**Сегодня:** отдельной метрики нет, но **все данные для неё есть**: график смен
по филиалам, исключения (`day_off`, `vacation`, `extra`, `override`),
`durationMinutes` у услуги, фактические приёмы с `scheduledAt`/`endsAt`.
То есть «занятые минуты / доступные минуты по графику» считается честно, с
вычетом отпусков и выходных.

`ВОПРОС РУКОВОДСТВУ:` считать по длительности услуг или по числу слотов?
Врач без заполненного графика — исключать из знаменателя или считать нулевую
загрузку?

### 6.5. Что такое лид

**Сегодня:** сущности лида нет (см. 4.7). Единственный измеримый вход —
**бронь с витрины**: у неё есть статус, дата, источник и признак
материализации в приём. Звонки и сообщения в системе не фиксируются вовсе.

`ВОПРОС РУКОВОДСТВУ:` считаем лидом только онлайн-заявку (тогда метрика
доступна сразу) или нужен учёт звонков (тогда это отдельная разработка)?

### 6.6. Средний чек

**Сегодня:** не считается нигде. Данных достаточно: сумма по приёму и по
строкам, товары внутри приёма, самостоятельные продажи отдельно.

`ВОПРОС РУКОВОДСТВУ:` на визит или на клиента? Включать ли товары и допуслуги?
(Технически товары внутри приёма входят в его сумму, продажи со склада — нет.)

### 6.7. Какие статусы попадают в отчёты

**Сегодня:** в денежные срезы — `paid` и `discounted`. Отменённые и неявки
остаются в истории, в выручку не попадают. Признаков «тестовая запись»,
«внутренний приём сотрудника», «льготная категория» в модели **нет** —
отфильтровать их сегодня нечем. Есть статус `free` (бесплатно) и `insurance`
(оплачено страховой) — их можно считать отдельными категориями.

`ВОПРОС РУКОВОДСТВУ:` нужны ли признаки тестовых и внутренних приёмов?
Если да — это доработка модели на бэке, до старта дашборда.

## 7. Технический стек

- **Фронтенд CRM (существующий):** React 18 + TypeScript + Vite + Refine +
  MUI v6, React Hook Form, dayjs, i18next. 565 файлов, 64 маршрута.
  ⚠ Расходится с заявленным для ErkinAI стеком (shadcn/ui + Zod) — если
  дашборд встраивается в CRM, он будет на MUI; если это отдельное приложение,
  их два. `ВОПРОС РУКОВОДСТВУ:` встраиваем или отдельный продукт?
- **Фронтенд ErkinAI (планируемый):** React + TypeScript, shadcn/ui,
  React Hook Form + Zod.
- **Бэкенд:** Django; слой API — не классический DRF, а msgspec-схемы
  (бэкенд называет слой «dmr»). Пагинация в стиле DRF
  (`{results, count, next, previous}`), snake_case на бэке → camelCase на фронте.
  Репозиторий чужой, ведёт отдельная команда.
- **БД:** `ВОПРОС БЭКЕНДУ` — фронтенду не видна. Требование materialized views
  предполагает PostgreSQL; подтвердить у бэкенда до планирования вьюх.
- **Аутентификация и права:** CRM — сессионная кука (`credentials: include`),
  401 поднимает событие `mamadoc:api-unauthorized`. Пациент на витрине — вход
  по SMS, дальше токен `X-Patient-Token`. Контекст организации — заголовок
  `X-Organization-Id` (побеждает legacy `?organizationId=`), плюс `X-Branch-ID`
  на отдельных ручках. Права — permission-коды, роли настраиваются организацией
  (см. §3).
- **Планировщик:** ⚠ **Celery в проекте нет.** Периодические задачи сделаны
  management-командами по планировщику ОС (так работают поллеры задач и ночной
  пересчёт достижений: 15–60 мин / час / ночь). Для §8 это значит: рефреш
  materialized views делается тем же способом, отдельной командой в кроне.
  Закладывать Celery-beat нельзя, не спросив бэкенд.
- **Интеграции:** `iwork.operator.kg` (партнёрское API броней — чужой продукт,
  мы клиент), Бакай (предоплата ссылкой + вебхук), SMS (коды входа и
  напоминания), Profigram (телемедицинские приглашения), Geoapify /
  Nominatim-совместимый геокодер (подсказки адресов), СКУД (распознавание лиц,
  смены по офисному IP).
- **Формат ошибок API:** ⚠ расходится между средами. На тестовом бэке новый
  конверт `{error:{code,message,details,trace_id}}` с 21 кодом, на проде — старый
  `{detail:[...]}`.

## 8. Аналитический слой

Раздел заполняется на шаге 2 (спецификация дашборда). Здесь фиксируется:
список вьюх, метрик, формулы, частота рефреша, контракты API.

**Уже принятые решения:**

- Агрегаты не считаются на каждый запрос — только через VIEW / MATERIALIZED VIEW
  с обновлением по расписанию.
- Разделяются два понятия: **период просмотра** (выбирает пользователь: день/неделя/месяц)
  и **частота пересчёта** (крон: час/сутки). В UI каждого блока показывается
  время последнего обновления данных.
- Каждая вьюха отдаёт не только текущее значение, но и **baseline** (среднее за 30 дней) —
  без него не будет ни дельт на дашборде, ни поиска отклонений у ИИ.

**Что уже считается в CRM** (можно переиспользовать или свериться, чтобы цифры
дашборда не разошлись с существующими отчётами):

| Эндпоинт | Что отдаёт |
|---|---|
| `/reports/monthly/` | месячная сводка: приёмы, деньги, дневные и ночные |
| `/reports/load/` | нагрузка |
| `/cashbox/summary/` | итоги кассы, разрез по способам оплаты, смены |
| `/payroll/report/` | заработок, авансы, остаток к выплате |
| `/warehouse/sales/stats/` | продажи товаров |
| `/reviews/stats/` | оценки |
| `/tasks/summary/`, `/tasks/stats/me/` | задачи |
| `/cleaning/summary/` | уборка |
| `/vaccinations/monthly-report/` | прививки |
| `/appointments/day-counts/` | загрузка по дням |
| `/scheduling/availability/summary/` | доступность и окна |

⚠ `/appointments/home/` **не дашборд**, несмотря на имя: это агрегат экрана
регистратуры (приёмы дня + счётчики + отметка изменений).

⚠ Главного экрана в CRM сейчас нет: `/` и `/home` — редирект на рабочий экран
пользователя. Задача «редактируемый главный экран» висит на доске с 12.07.2026.

⚠ Известные ограничения существующей отчётности, которые нельзя унаследовать:
реестры тянут период целиком без пагинации (месяц ≈ 3,1 МБ); часть агрегатов
бэк не режет по филиалу.

## 9. AI-сводка

Раздел заполняется на шаге 4. Уже принятые решения:

- Генерация в 22:00, показ — как утренний брифинг (соответствует презентации).
- Результат сохраняется снапшотом в БД, не перегенерируется при каждом открытии.
- Доставка: в интерфейс. Telegram — следующим этапом.
- **В модель уходят только агрегаты и ID, без имён, диагнозов и любых персональных
  данных.** Это снимает вопрос чувствительности медданных на уровне архитектуры.
- Формат карточки: что происходит → почему → цена вопроса в деньгах → действие с дедлайном.

⚠ Генерация по расписанию упирается в тот же планировщик, что и §8: Celery нет,
только management-команда в кроне ОС.
