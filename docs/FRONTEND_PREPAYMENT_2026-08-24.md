# Онлайн-предоплата: что делать фронту — 24.08.2026

Бэкенд наряда B выложен: ветка `claude/what-is-needed-fjjetp` в
`MamaDoc-backend`, коммит `8ceb9cb`. Контракт целиком —
`docs/bookings-contract.md` §6 и `docs/backend-reply-2026-08-24-prepayment-part-b.md`
в бэкенд-репозитории.

Суть: пациент платит предоплату на витрине, и эти деньги теперь **сами**
доезжают до денег приёма — отдельной строкой оплаты (`card`, способ безнала
«Бакай Paylink», дата кассы = день фактической оплаты). Долг, касса и отчёты
считаются как раньше, новых сущностей на фронте не появилось.

## 1. Форма оплаты приёма — сначала это

**Что сломается без правки.** `DjangoPaymentDrawer.tsx:374-381` подставляет в
поля суммы всех платежей по методу:

```ts
const cardSum = sumByMethod("card");   // ← сюда попадает и предоплата
setCard(cardSum > 0 ? cardSum : "");
```

Предоплата — это `card`-строка. Приём на 1500 с предоплатой 500 откроется с
«Карта 500»; регистратор добавит 1000 наличными и нажмёт «Сохранить» →
уйдёт `payments: [{cash 1000}, {card 500}]` → бэк ответит **400 «Переплата
запрещена»**. Причина: строка предоплаты защищена от replace-all и остаётся в
журнале сама, а сумма к оплате уже уменьшена на неё (1000). Присылать её
обратно не нужно и нельзя — у неё дата кассы вне разрешённых пресетов
(«сегодня» / «дата приёма»).

**Что поправить:**

1. **Исключить предоплату из сидирования** (`:374`, и то же самое в блоке
   `:481`):

```ts
const manualPayments = (summary.payments ?? []).filter((p) => !p.isPrepayment);
const sumByMethod = (method: string) =>
  manualPayments
    .filter((p) => p.method === method)
    .reduce((acc, p) => acc + parseDecimal(p.amount), 0);
```

   То же для сидирования способа безнала (`:394`) и выбора даты кассы (`:400`):
   брать первую **не**-предоплатную `card`-строку, иначе форма подхватит
   «Бакай Paylink» и чужую дату кассы и молча перезапишет ими выбор
   регистратора.

2. **Вычесть предоплату из суммы к оплате** (`:525-527`) — иначе превью долга
   врёт: сейчас после ввода 1000 форма покажет долг 500, а бэк вернёт 0.

```ts
const prepaid = parseDecimal(summary?.prepaidTotal);
const payable = Math.max(0, (…текущий расчёт…) - prepaid);
```

   `debt` считается от этого же `payable` (`:566-568`), так что дальше всё
   встанет само. Проверка `overpaid` (`:534`) тоже станет верной: 1500 поверх
   предоплаты честно подсветится в форме, а не улетит в 400.

3. **Показать предоплату в списке платежей** (`:1381-1400`) — отдельной
   строкой, чтобы регистратор видел, откуда взялись деньги и почему долг
   меньше стоимости:

```tsx
{p.isPrepayment && <Chip size="small" label={`Онлайн-предоплата · ${p.cashDate}`} />}
```

   Дата у неё — день оплаты брони, не приёма. Правки строка не требует и
   удалиться не может.

4. **`overpaidAmount`** — приём дешевле предоплаты (записались без выбора
   услуги, а приём вышел на 300 при предоплате 500) закрывается как `paid`,
   долг 0, а разница приходит в `overpaidAmount`. Показать её как
   «Переплата 200» рядом со статусом. Что с переплатой делать дальше —
   открытый вопрос к заказчику, UI под это пока не проектируем.

### Новые поля в типах

`src/api/payments.ts`:

```ts
export interface AppointmentPayment {
  // …
  /**
   * Строка пришла онлайн-предоплатой брони, а не из кассы. Её нельзя
   * перезаписать обычной оплатой и не нужно присылать в apply.
   * `undefined` — окружение без релиза предоплаты.
   */
  isPrepayment?: boolean;
}

export interface PaymentSummary {
  // …
  /** Онлайн-предоплата, уже проведённая в приём (входит в paidTotal). */
  prepaidTotal?: string;
  /** Уплачено сверх суммы к оплате: долг в минус не уходит, разница здесь. */
  overpaidAmount?: string;
}
```

Оба поля опциональные по той же причине, что `onlineBookingEnabled` в
`staff.ts`: на окружении без релиза их нет, и `undefined` должен читаться как
«предоплат тут не бывает» (`parseDecimal(undefined)` → 0, поведение как
раньше).

## 2. Карточка сотрудника: галочка + сумма

Сумма предоплаты — **своя у каждого врача** (заказчик пересмотрел решение
23.08.2026). Никаких орг-настроек: в CRM-настройках организации этого поля быть
не должно, и снимать оттуда нечего — фронт `/api/bookings/settings/` не
вызывает вообще.

`GET /api/staff/employees/` и `/{id}/`, `POST`, `PATCH` отдают и принимают:

| Поле | Тип | Замечание |
|---|---|---|
| `prepaymentRequired` | `boolean` | уже есть в `staff.ts`, в UI ещё нет |
| `prepaymentAmount` | `string` | decimal-строка, напр. `"500.00"`; принимает и число |

**Правило, которое легко нарушить:** включить `prepaymentRequired` без суммы
нельзя — бэк отвечает `400`. Врач с флагом и суммой 0 означал бы «оплатите
0 сом, чтобы записаться». Поэтому галочку и поле суммы отправляем **одним**
`PATCH`, а сохранение блокируем, пока при включённой галочке сумма пустая или
нулевая. Отрицательная сумма — тоже `400`.

Правка телефона у врача, у которого исторически флаг есть, а суммы нет, не
падает: проверка срабатывает только когда запрос трогает одно из этих двух
полей.

`src/api/staff.ts` — добавить в `DjangoEmployee` (`:77`),
`DjangoEmployeeListItem` (`:105`), `CreateEmployeePayload` (`:120`),
`UpdateEmployeePayload` (`:178`):

```ts
/** Сумма онлайн-предоплаты этого врача, decimal-строка ("500.00"). */
prepaymentAmount?: string;
```

`DjangoEditEmployeeDrawer.tsx` — рядом с `onlineBookingEnabled` (`:165`, `:194`,
`:250`), тем же паттерном «поле может отсутствовать на окружении»: если бэк
поля не знает — не показывать и не слать, иначе `400 unknown field` отклонит
всю форму. Не забыть добавить поле в сравнение «форма изменилась» (`:188-205`),
иначе кнопка «Сохранить» останется серой.

Витрина (`/api/v1/professionals/{id}/`) уже отдаёт `prepayment_amount` этого
врача — публичная часть правок не требует.

## 3. Очередь «Брони»

### Новый статус `awaiting_payment`

Бронь к врачу с предоплатой создаётся витриной в статусе `awaiting_payment` и
ждёт банк. Слот она держит, но администратору делать с ней нечего: **подтвердить
её нельзя** — бэк ответит `400`. После подтверждения оплаты банком бронь сама
переходит в `pending` и появляется в обычной очереди.

`src/api/bookings.ts:24` — добавить в `BookingStatus`. `BookingManageStatus`
(`:32`) должен исключать и его:

```ts
export type BookingStatus =
  | "awaiting_payment"
  | "pending"
  | "confirmed"
  | "cancelled"
  | "completed"
  | "no_show";

export type BookingManageStatus = Exclude<
  BookingStatus,
  "pending" | "awaiting_payment"
>;
```

`src/pages/bookings/meta.tsx` — чип и опция фильтра (`:15`, `:22`):
`awaiting_payment` → «Ждёт оплаты», тон `default`/нейтральный (это ещё не
заявка). В `bookingTimeHint` (`:130`) такую бронь просроченной звать не стоит —
её снимет поллер сам.

В карточке и в списке спрятать кнопку «Подтвердить» при
`status === "awaiting_payment"`, иначе пользователь получит 400 без объяснения
(`ConfirmBookingDialog.tsx`, `BookingDetailDrawer.tsx:208`).

### Новые поля брони

```ts
export type BookingPrepaymentStatus =
  | "none"          // предоплата не требуется
  | "pending"       // ссылка выставлена, банк молчит
  | "paid"          // банк подтвердил, в приём деньги ещё не проведены
  | "applied"       // проведена в приём (см. prepaymentPaymentId)
  | "unallocated";  // оплачена, а приёма не будет — деньги повисли

export interface BookingListItem {
  // …
  prepaymentStatus?: BookingPrepaymentStatus;
  /** Фактически оплаченная сумма, decimal-строка. */
  prepaymentAmount?: string;
  /** ISO-время оплаты по данным банка. */
  prepaymentPaidAt?: string | null;
  /** До этого момента бронь держит слот; null — резерв не ограничен. */
  reserveExpiresAt?: string | null;
}

export interface BookingDetail extends BookingListItem {
  // …
  /** Строка оплаты приёма, в которую проведена предоплата. */
  prepaymentPaymentId?: number | null;
}
```

Что показать:

- **в списке** — сумму и статус оплаты рядом со статусом брони. Оплаченная
  бронь (`paid`) должна визуально отличаться от неоплаченной: администратор
  подтверждает в первую очередь её;
- **`reserveExpiresAt`** — «резерв истекает через N мин». Это ответ на вопрос
  «почему бронь исчезла»: по истечении её отменяет поллер. У оплаченной брони
  таймер не работает — деньги пришли, дальше решает администратор;
- **`unallocated`** — деньги есть, приёма не будет (отмена, неявка, отказ).
  Такие брони специально остаются на виду; нужен заметный маркер и фильтр
  `?prepaymentStatus=unallocated` в панели фильтров (бэк его поддерживает,
  см. ниже). Куда девать эти деньги — открытый вопрос к заказчику, кнопок
  «вернуть»/«на баланс» пока не рисуем.

### Фильтры

`GET /api/bookings/` принимает `?prepaymentStatus=` (те же 5 значений) плюс
`?status=awaiting_payment`. Добавить в `BookingsFilters` (`:113`) и в сборку
query (`:138`).

## 4. Публичная страница результата оплаты

`GET /api/v1/bookings/<confirmationCode>/` теперь отдаёт `payment`:

```json
{ "payment": { "status": "paid", "amount": "500.00", "paid_at": "2026-08-24T12:30:00+00:00" } }
```

`null` — у брони без предоплаты. Кнопка банка «Я оплатил(а)» ничего не
доказывает, поэтому страницу результата надо опрашивать этой ручкой:
`status: "paid"` (или `applied`) = деньги дошли. Ссылку на оплату в этот же
объект добавит наряд A — ключи не конфликтуют, ломать ничего не придётся.

## Чего делать НЕ нужно

- **Снимать контрол суммы предоплаты из настроек организации** — во фронте его
  нет: `/api/bookings/settings/` не вызывается ни из одного файла. Орг-поле на
  бэке осталось только ради совместимости и ни на что не влияет.
- **Проектировать UI для переплаты и «денег без приёма»** — оба вопроса ушли
  заказчику. Бэк деньги не теряет и никуда молча не переносит; когда решение
  будет, добавим механику.
- **Присылать строку предоплаты в apply** — она живёт сама и защищена от
  перезаписи.

## Как проверить руками

Наряд A (ссылки Бакая) ещё не готов, но проверить весь путь можно из shell
бэкенда:

```python
from server.apps.bookings.models import Booking
from server.apps.bookings.services import mark_booking_prepayment_paid
from django.utils import timezone

b = Booking.objects.get(confirmation_code='XXXXXXXXXX')
mark_booking_prepayment_paid(b, '500.00', timezone.now(), 'test-ref-1')
```

Дальше — подтвердить бронь в CRM и открыть оплату приёма: долг должен быть
меньше стоимости ровно на 500, а в списке платежей появиться строка
«Онлайн-предоплата» с датой оплаты.
