# Контракт бэкенда после фиксов

Дата: 03.08.2026  
Репозиторий бэкенда: `C:\Users\laby\Desktop\MamaDoc-backend`

Документ объединяет четыре тикета. Основные затронутые контексты:

- организация **«Мама Доктор»** — филиалы **«Мама Доктор»**, **«Мама Доктор Плюс»** и **«Тестовый филиал»**;
- организация **«Клиника 21»** — филиал из тикета кассы не имеет названия в исходных данных, поэтому в API используйте выбранный `branchId` текущего контекста.

## 1. Медицинское заключение: очистка витальных показателей

Эндпоинт: `PATCH /api/medical/conclusions/<id>/`

Подтверждённый контракт:

- поле отсутствует в JSON — значение не меняется;
- `null` — значение очищается;
- пустая строка `""` или строка из пробелов — также очищает значение;
- имена только camelCase: `weightKg`, `heightCm`, `temperature`.

Пример:

```json
{
  "weightKg": null,
  "heightCm": null,
  "temperature": null
}
```

В успешном ответе очищенные поля имеют значение `null`. Флаги `clearWeightKg`, `clearHeightCm`, `clearTemperature` и snake_case-поля не нужны.

## 2. Онбординг сотрудника

Эндпоинт: `POST /api/staff/employees/onboard/`

Успешный запрос фронта остаётся прежним. Минимально нужно передать `fullName`, `roleId`, `employeeBranchIds` и один из `userId`, `username`, `email`, `phone`.

Успех: `201` с объектом:

```json
{
  "employee": {},
  "user": {},
  "membership": {},
  "employeeBranches": [],
  "userBranches": []
}
```

Исправления на бэкенде:

- повторяющиеся branch/specialization id нормализуются и не приводят к падению на уникальном ограничении;
- предсказуемый конфликт базы возвращается как `400`, транзакция откатывается;
- при ошибке не показывать пользователю успешное создание, пока не получен `201`.

Ошибки формы по-прежнему приходят в стандартном формате `detail[].msg`. Если после этого фикса корректный запрос снова даст `500`, фронту не нужно подбирать другой payload — требуется передать бэкенду traceback и тело запроса.

## 3. Остаток товара по филиалу

Эндпоинты:

- `GET /api/warehouse/products/`
- `GET /api/warehouse/warehouses/`
- `GET /api/warehouse/stock/`

`branchId` теперь является реальным фильтром. Для суперпользователя передавайте оба параметра:

```text
/api/warehouse/products/?organizationId=1&branchId=13
```

В ответе товара:

- `stock` сохранён для обратной совместимости и может быть агрегатом видимых складов;
- `branchStock` — остаток именно на складе, который будет использован для списания товара в приёме;
- при отсутствии `branchId` `branchStock` равен `null`.

Правило выбора склада для приёма: склад продаж (`isSales`) → основной склад (`isPrimary`) → склад филиала с минимальным id. Подключённые склады другого филиала видны в инвентарном списке, но автоматически не выбираются для списания товара в приёме.

Для проблемного примера ожидайте:

- филиал **«Мама Доктор Плюс»**: `branchStock: "0.000"`;
- филиал **«Мама Доктор»**: `branchStock: "174.000"`.

В пикере приёма используйте `branchStock`, если он не `null`, и не фильтруйте товар по старому `stock`.

## 4. Машиночитаемая ошибка нехватки товара

При создании или изменении приёма ответ остаётся `400`, но деталь теперь содержит код и контекст склада:

```json
{
  "detail": [{
    "msg": "Недостаточно товара …",
    "type": "insufficient_stock",
    "code": "insufficient_stock",
    "productId": 27,
    "warehouseId": 7,
    "warehouseName": "Склад (Сейтек)",
    "required": 1,
    "available": "0.000"
  }]
}
```

Фронт должен проверять `detail[0].code`, а не разбирать русский текст регулярным выражением. Показывайте ошибку в строке товара и название склада из `warehouseName`.

## 5. Касса и возврат товара

Для фронта отдельный workaround не нужен.

Автоматический возврат товара при отмене/изменении приёма сохраняет движение склада, но больше не считается закупкой и не попадает в `supplyCashExpenses`, `supplyCardExpenses`, `supplyTotal` или `GET /api/cashbox/entries/?entryType=supply`.

В кассовые закупки попадают только положительные ручные приходы с явно указанным `paymentMethod` (`cash` или `cashless`). `paymentMethod: null` больше не считается наличными.

Количество товара на складе при этом не меняется: возврат остаётся складским движением.

## Чеклист интеграции

- [ ] В заключении при пустом поле отправлять `null`.
- [ ] Для списка товаров передавать `organizationId` и активный `branchId`.
- [ ] В пикере использовать `branchStock`, а не `stock`, когда передан филиал.
- [ ] Обработать `type/code === "insufficient_stock"` без парсинга текста.
- [ ] После онбординга считать операцию успешной только при HTTP `201`.
- [ ] Для кассы не добавлять клиентскую фильтрацию возвратов — бэкенд уже исключает их из кассовых агрегатов.
- [ ] Проверить `npx tsc --noEmit` и сценарии смены филиала с инвалидированием React Query-кэша.
