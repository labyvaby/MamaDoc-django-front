# Отель Viva: что нужно от бэкенда (запросы от 02.10.2026)

Встреча с заказчиком 02.10.2026: график персонала с суточными сменами и
зарплатой по нему, разные валюты, право менять цену «чего угодно в любой
момент», реквизиты в счетах, отчёты по ролям. Всё, что можно было сделать на
существующем API, фронт уже сделал (отчёты «Собственнику», «Смена
администратора», «Балансы броней», Excel-выгрузки, импорт гостей, проверка
номера перед выездом). Ниже — то, без чего дальше нельзя.

Общее для всех разделов: формат как у остального `/api/v2/hotel/` (camelCase,
деньги — строки `"3500.00"`, даты — `YYYY-MM-DD`, время — ISO с часовым поясом
объекта), правка записей с `version` → `409 VERSION_CONFLICT`, ошибки полей —
`400` с телом, как сейчас. Где фронт уже готов — он сам включится, когда
эндпоинт начнёт отвечать не `404`.

Приоритет по словам заказчика: **1 → 2 → 3 → 4**, остальное — по мере сил.

## 1. График персонала: посты и смены (в т. ч. суточные)

Сейчас Viva ведёт график в Google Sheets: строка — день, колонки — посты
(«1 этаж», «2 этаж», «3 этаж» — горничные по этажам, «Кухня», «Ресепшн»), в
ячейке — имя сотрудника. Ресепшен работает сутками (09:00 → 09:00), горничные —
днём. Расписание клиники (`/scheduling/`) не подходит: смены через полночь там
запрещены (`end_time > start_time`), и в нём нет постов.

### Посты объекта

```http
GET    /api/v2/hotel/staff-posts/?propertyId=7            # hotel.view
POST   /api/v2/hotel/staff-posts/                         # hotel.staff.manage
PATCH  /api/v2/hotel/staff-posts/{id}/                    # hotel.staff.manage
DELETE /api/v2/hotel/staff-posts/{id}/                    # архив, история смен остаётся
```

```json
{
  "id": 3,
  "propertyId": 7,
  "name": "2 этаж",
  "role": "housekeeping",
  "floors": ["2"],
  "startTime": "09:00",
  "hours": 12,
  "rate": "2000.00",
  "sortOrder": 20,
  "isActive": true
}
```

| Поле | Тип | Значение |
| --- | --- | --- |
| `role` | enum | `housekeeping`, `reception`, `kitchen`, `maintenance`, `other` — для зарплаты по ролям и отчётов |
| `floors` | string[] | Этажи поста (значения `Room.floor`) — только у `housekeeping`; по ним уборка распределяется по графику (§3) |
| `startTime`, `hours` | time, int 1–24 | Начало и длительность смены по умолчанию; `hours: 24` — сутки, конец на следующий день |
| `rate` | Money | Ставка за смену в валюте объекта (у Viva: горничная 2000, повар 2000, ресепшен 3000) |

### Смены

```http
GET /api/v2/hotel/staff-shifts/?propertyId=7&from=2026-09-01&to=2026-09-30   # hotel.staff.view, период ≤ 62 дней
PUT /api/v2/hotel/staff-shifts/                                              # hotel.staff.manage
```

`GET` — смены, которые **начинаются** в `[from, to]` (обе даты включительно):

```json
[
  {
    "id": 101,
    "propertyId": 7,
    "postId": 5,
    "postName": "Ресепшн",
    "role": "reception",
    "date": "2026-09-01",
    "employeeId": 42,
    "employeeName": "Биймырза",
    "startsAt": "2026-09-01T09:00:00+06:00",
    "endsAt": "2026-09-02T09:00:00+06:00",
    "rate": "3000.00",
    "status": "planned",
    "note": ""
  }
]
```

`PUT` — пакетная правка сетки (так её редактируют: кликнул ячейку — выбрал
человека); одна смена на пост в день, ключ — `(postId, date)`:

```json
{
  "propertyId": 7,
  "shifts": [
    { "postId": 5, "date": "2026-09-01", "employeeId": 42 },
    { "postId": 3, "date": "2026-09-01", "employeeId": 17, "rate": "2500.00", "note": "за двоих" },
    { "postId": 1, "date": "2026-09-02", "employeeId": null }
  ]
}
```

- `employeeId: null` — снять смену (удалить строку);
- `rate` не передан — берётся текущая ставка поста и **замораживается** в смене
  (поменяли ставку поста в октябре — сентябрь не пересчитывается);
- `startsAt/endsAt` считаются из `startTime/hours` поста, можно передать свои;
- `status`: `planned` → `worked` / `absent` (отметка факта, по умолчанию
  `planned` считается отработанной в прошлом);
- сотрудник другой организации → `400`; один сотрудник в двух сменах, которые
  пересекаются по времени, → `409 SHIFT_OVERLAP` с `conflicts`, повтор с
  `allowOverlap: true` — сохранить (у Viva бывает: «Мунара» на 1 и 3 этаже в
  один день — это норма, поэтому не запрет, а предупреждение).

Права: `hotel.staff.view` (видеть график — все сотрудники отеля),
`hotel.staff.manage` (составлять — управляющий/старший админ).

## 2. Зарплата по графику

Фронт посчитает сам по сменам и авансам — от бэкенда нужен только §1:

- начислено = Σ `rate` отработанных смен сотрудника за месяц, с разбивкой по
  `role` (как в их таблице: 🧽 / 👩‍🍳 / 📋 и «Всего»);
- аванс = Σ расходов финансов категории `kind: "advance"` на этого сотрудника
  с `affectsMonth` = месяц (уже есть: `/finance/expenses/?employeeId=…`);
- к выплате = начислено − аванс.

Если удобнее считать на бэке (закрытие месяца, блокировка задним числом),
вот ответ, который фронт примет без переделки:

```http
GET /api/v2/hotel/staff-payroll/?propertyId=7&month=2026-09     # hotel.staff.manage
```

```json
{
  "month": "2026-09",
  "currency": "KGS",
  "rows": [
    { "employeeId": 17, "employeeName": "Мунара", "shiftsByRole": { "housekeeping": 30, "kitchen": 1 }, "shifts": 31, "earned": "62000.00", "advances": "19000.00", "toPay": "43000.00" }
  ],
  "totals": { "earned": "356000.00", "advances": "145280.00", "toPay": "210720.00" }
}
```

## 3. Уборка по этажам из графика

```http
POST /api/v2/hotel/housekeeping-tasks/assign-by-roster/      # hotel.housekeeping.manage
{ "propertyId": 7, "date": "2026-10-02", "onlyUnassigned": true }
→ { "assigned": 14, "skipped": 2, "unmatchedFloors": ["4"] }
```

Открытые задачи дня по номерам этажа поста получают `assignedTo` = горничную
этого поста на эту дату. Хорошо бы так же автоматически назначать задачи,
которые бэкенд сам создаёт при выезде.

## 4. Цена «чего угодно в любой момент»: цена ночи, скидка, сумма при создании

Заказчик: «хотят иметь доступ менять цену чего угодно в любой момент»,
«сумму при редактировании можно менять, по умолчанию стоит цена, которая
высчитывается автоматически». Сейчас ночи брони замораживаются при создании,
`ItemUpdatePayload` цену не принимает, а допуслуги не бывают отрицательными.

### Цены ночей и скидка номера в брони

```http
PATCH /api/v2/hotel/reservations/{id}/items/{itemId}/pricing/     # hotel.prices.override
{
  "version": 12,
  "nights": [
    { "date": "2026-10-01", "price": "3500.00" },
    { "date": "2026-10-02", "price": null }
  ],
  "discountPercent": "10",
  "reason": "Постоянный гость, договорились по телефону"
}
→ ReservationDetailPayload
```

- `price: null` — вернуть расчётную цену ночи; ночь вне дат номера → `400`;
- `discountPercent` (0–100, `null` — без скидки) применяется к каждой ночи;
- пересчитать сумму номера, брони и баланс; в историю (`logs`) —
  `action: "price_changed"` со старыми/новыми ценами по датам, скидкой,
  причиной и сотрудником; `reason` обязателен;
- в `ReservationNightPayload` добавить `basePrice` (расчётная), `discount`
  (сумма скидки ночи) и `isManual` — фронт покажет «изменено вручную»
  и «вернуть расчётную».

### Своя сумма при создании и изменении

В `ReservationItemInput` (создание) и `ItemUpdatePayload` — необязательное
`manualTotal: Money`: сумма за весь номер; бэкенд раскладывает её по ночам
поровну (остаток — на последнюю ночь), помечает ночи `isManual` и пишет в
историю. Без поля — как сейчас.

Новое право `hotel.prices.override` (суперадмин — как всегда, без права).

## 5. Валюты: курсы объекта и оплата в валюте

Гости платят долларами, евро, рублями, тенге. Нужны курсы объекта и
`currency` в оплате. Отображение в другой валюте («режим валют») фронт сделает
сам по этим курсам.

```http
GET /api/v2/hotel/properties/{id}/exchange-rates/        # hotel.view
PUT /api/v2/hotel/properties/{id}/exchange-rates/        # hotel.payments.manage
```

```json
{
  "baseCurrency": "KGS",
  "rates": [
    { "currency": "USD", "rate": "87.45", "updatedAt": "2026-10-02T09:10:00+06:00", "updatedByName": "Биймырза" },
    { "currency": "EUR", "rate": "101.20", "updatedAt": "…", "updatedByName": "…" }
  ]
}
```

`rate` — сколько базовой валюты за 1 единицу. `PUT` принимает `{ "rates":
[{ "currency": "USD", "rate": "87.50" }] }`, валюты не из списка удаляются.

Оплата (`POST /reservations/{id}/payments/`) — новые необязательные поля:

```json
{ "method": "cash", "amount": "50.00", "currency": "USD", "exchangeRate": "87.50", "kind": "payment" }
```

- без `currency` — как сейчас (базовая валюта);
- `exchangeRate` не передан — текущий курс объекта; нет курса → `400`;
- в оплате хранить `amount` + `currency` (что дал гость) и `amountBase`
  (в валюте объекта) — баланс брони считается по `amountBase`;
- `PaymentPayload`: добавить `amountBase`, `exchangeRate`, `baseCurrency`;
- реестр кассы: группы `totals` уже «способ × валюта» — так и оставить
  (наличные доллары лежат в кассе отдельно), плюс `netBase` в каждой группе;
- возврат — в той же валюте, по курсу на момент возврата.

## 6. Реквизиты объекта для счёта и справки

Счёт на оплату и справка о проживании уже печатаются с блоком реквизитов —
он появится, когда в `PropertyPayload` (и в `PATCH /properties/{id}/`, право
`hotel.manage`) будут поля, все строки, необязательные:

| Поле | Пример |
| --- | --- |
| `legalName` | ОсОО «Вива Отель» |
| `legalAddress` | г. Бишкек, ул. Киевская, 1 |
| `inn` | 01234567890123 |
| `okpo` | 12345678 |
| `taxAuthority` | УГНС по Первомайскому району |
| `bankName` | ОАО «Kompanion Bank» |
| `bankAccount` | 1234567890123456 |
| `bik` | 123456 |

| `accountantName` | Петрова А. А. |

## 7. Шахматка: оплата в элементах календаря

В `CalendarItemPayload` добавить `paidAmount`, `balanceDue`, `currency`
брони. Сейчас долг на брони шахматки фронт добирает отдельным списком броней
за видимые даты — лишние запросы на каждую прокрутку.

## 8. Уборка: закрытые задачи, связь с бронью, отчёт по горничным

1. `GET /housekeeping-tasks/` при `status=done|cancelled` отдаёт **все**
   закрытые задачи без ограничений — для отчётов нужны `completedFrom`,
   `completedTo` и пагинация `limit/offset` → `{ count, results }` (старый
   ответ-массив можно оставить, когда `limit` не передан).
2. В `HousekeepingTaskPayload` — `completedById`, `completedByName`,
   `startedAt`; в создание — `reservationItemId`. Проверка номера перед
   выездом (сделана на фронте) сейчас хранит номер брони и результат в
   `note` и держит задачу «в работе» до выселения, потому что закрытую задачу
   не найти. С `reservationItemId` и фильтром `reservationItemId=` в списке —
   переделаем на нормальную связь.
3. Отчёт по горничным:
   `GET /api/v2/hotel/reports/housekeeping/?propertyId=7&from=…&to=…` →
   по сотрудникам: выполнено задач по видам, среднее время от `startedAt` до
   `completedAt`, по дням.

## 9. Отчёт смены: звонки и сообщения

Админ в конце смены пишет число звонков (Мегаком, О!) и сообщений в
WhatsApp. Сейчас фронт хранит их на устройстве админа до печати.

```http
GET /api/v2/hotel/shift-notes/?propertyId=7&date=2026-10-02     # hotel.payments.manage
PUT /api/v2/hotel/shift-notes/                                  # hotel.payments.manage
{ "propertyId": 7, "date": "2026-10-02", "callsMegacom": 14, "callsO": 9, "whatsappMessages": 31, "comment": "" }
```

## 10. Гости: весь список для выгрузки

`GET /hotel/guests/` отдаёт не больше 200 строк. Для «Выгрузить в Excel» и
проверки дублей при импорте нужны `limit/offset` и `count` (как у броней).

## 11. Ошибка: привязка юрлица к брони → 500

`PATCH /api/v2/hotel/reservations/{id}/` с `corporateAccountId` отвечает
`500` (trace `3fac135c-f653-4353-95cc-d0e7ad569a8e`,
`2780402e-5a97-4bf3-bb84-a6f4e0eed9f6`, тест, 01.10.2026).

## 12. Брони по дате заезда

Для «Балансов броней» фронт берёт брони, пересекающие период, и режет по
дате заезда у себя. Фильтр `checkInFrom/checkInTo` в
`GET /reservations/` убрал бы лишние строки в длинных периодах.
