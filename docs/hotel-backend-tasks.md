- **Интерфейс уже готов** (фронт, ветка `test`). Где эндпоинта нет, работает
  демо-режим: данные хранятся на устройстве сотрудника или показывается
  пример, а на экране есть пометка «демо». В демо-режиме на сервер ничего не
  пишется.
- **Фронт переключается сам.** Он смотрит, ответил ли эндпоинт не `404`/`405`
  или появилось ли в ответе новое поле. Это «Признак» в каждом разделе. Где
  написано «включится сам», релиз фронта не нужен.
- **Проверено на `test.crm.operator.kg` 02.10.2026:**
  - все новые эндпоинты ниже отвечают `404`;
  - в объекте нет реквизитов;
  - в позициях календаря нет оплат;
  - фильтр `checkInFrom` в списке броней не работает;
  - список гостей отдаётся без пагинации.

  «События города» (`/city-events/`), терраса и фото номеров уже работают,
  поэтому в этом файле их нет.
- **Важно.** `POST /reservations/` молча пропускает незнакомые поля: с
  `manualTotal` ответ такой же, как без него, `400` нет (проверено
  заведомо невалидным запросом, ничего не создано). Поэтому фронт
  определяет поддержку по полям в ответе. Новые поля обязательно отдавайте в
  ответах, как описано ниже.

Общие правила — как у остального `/api/v2/hotel/`:

- имена полей в camelCase;
- деньги — строки `"3500.00"`;
- даты — `YYYY-MM-DD`, время — ISO с часовым поясом объекта;
- правка записи с `version` → `409 VERSION_CONFLICT`;
- ошибки полей — `400` с `details.fields`;
- всё ограничено организацией и филиалом сессии: чужой `propertyId` → `404`;
- списки, которые растут, отдаются с `limit/offset` → `{ count, results }`.

## 1. График персонала: посты и смены (в т. ч. суточные)

Сейчас Viva ведёт график в Google Sheets: строка — день, колонки — посты
(«1 этаж», «2 этаж», «3 этаж» — горничные по этажам, «Кухня», «Ресепшн»), в
ячейке — имя сотрудника. Ресепшен работает сутками (09:00 → 09:00), горничные —
днём. Расписание клиники (`/scheduling/`) не подходит: смены через полночь там
запрещены (`end_time > start_time`), и в нём нет постов.

### Посты объекта

```http
GET    /api/v2/hotel/staff-posts/?propertyId=7            # hotel.view
POST   /api/v2/hotel/staff-posts/                         # hotel.staff.manage
PATCH  /api/v2/hotel/staff-posts/{id}/                    # hotel.staff.manage
DELETE /api/v2/hotel/staff-posts/{id}/                    # архив, история смен остаётся
```

```json
{
  "id": 3,
  "propertyId": 7,
  "name": "2 этаж",
  "role": "housekeeping",
  "floors": ["2"],
  "startTime": "09:00",
  "hours": 12,
  "rate": "2000.00",
  "sortOrder": 20,
  "isActive": true
}
```

| Поле | Тип | Значение |
| --- | --- | --- |
| `role` | enum | `housekeeping`, `reception`, `kitchen`, `maintenance`, `other` — для зарплаты по ролям и отчётов |
| `floors` | string[] | Этажи поста (значения `Room.floor`) — только у `housekeeping`; по ним уборка распределяется по графику (§3) |
| `startTime`, `hours` | time, int 1–24 | Начало и длительность смены по умолчанию; `hours: 24` — сутки, конец на следующий день |
| `rate` | Money | Ставка за смену в валюте объекта (у Viva: горничная 2000, повар 2000, ресепшен 3000) |

### Смены

```http
GET /api/v2/hotel/staff-shifts/?propertyId=7&from=2026-09-01&to=2026-09-30   # hotel.staff.view, период ≤ 62 дней
PUT /api/v2/hotel/staff-shifts/                                              # hotel.staff.manage
```

`GET` — смены, которые **начинаются** в `[from, to]` (обе даты включительно):

```json
[
  {
    "id": 101,
    "propertyId": 7,
    "postId": 5,
    "postName": "Ресепшн",
    "role": "reception",
    "date": "2026-09-01",
    "employeeId": 42,
    "employeeName": "Биймырза",
    "startsAt": "2026-09-01T09:00:00+06:00",
    "endsAt": "2026-09-02T09:00:00+06:00",
    "rate": "3000.00",
    "status": "planned",
    "note": ""
  }
]
```

`PUT` — пакетная правка сетки (так её и редактируют: клик по ячейке — выбор
человека). Одна смена на пост в день, ключ — `(postId, date)`:

```json
{
  "propertyId": 7,
  "shifts": [
    { "postId": 5, "date": "2026-09-01", "employeeId": 42 },
    { "postId": 3, "date": "2026-09-01", "employeeId": 17, "rate": "2500.00", "note": "за двоих" },
    { "postId": 1, "date": "2026-09-02", "employeeId": null }
  ]
}
```

- `employeeId: null` — снять смену (удалить строку).
- `rate` не передан — берётся текущая ставка поста и **замораживается** в
  смене: поменяли ставку поста в октябре — сентябрь не пересчитывается.
- `startsAt` и `endsAt` считаются из `startTime/hours` поста; можно передать
  свои.
- `status`: `planned` → `worked` / `absent` — отметка факта. По умолчанию
  `planned` в прошлом считается отработанной.
- Сотрудник другой организации → `400`.
- Один сотрудник в двух сменах, которые пересекаются по времени, →
  `409 SHIFT_OVERLAP` с `conflicts`. Повтор с `allowOverlap: true` сохраняет.
  У Viva такое бывает («Мунара» на 1 и 3 этаже в один день — это норма),
  поэтому это предупреждение, а не запрет.

Права:

- `hotel.staff.view` — видеть график (все сотрудники отеля);
- `hotel.staff.manage` — составлять график (управляющий, старший админ).

**Сейчас на фронте.** «Персонал → График» показывает пример по таблице отеля
за сентябрь (`staffRosterDemo.ts`); правки живут в памяти вкладки.
**Признак:** `GET /staff-posts/` не `404` — фронт включится сам.

## 4. Цена «чего угодно в любой момент»: цена ночи, скидка, своя сумма брони

Заказчик: «хотят иметь доступ менять цену чего угодно в любой момент»,
«сумму при редактировании можно менять, по умолчанию стоит цена, которая
высчитывается автоматически». Сейчас ночи брони замораживаются при создании, и
`ItemUpdatePayload` цену не принимает.

### Цены ночей и скидка номера в брони

```http
PATCH /api/v2/hotel/reservations/{id}/items/{itemId}/pricing/     # hotel.prices.override
{
  "version": 12,
  "nights": [
    { "date": "2026-10-01", "price": "3500.00" },
    { "date": "2026-10-02", "price": null }
  ],
  "discountPercent": "10",
  "reason": "Постоянный гость, договорились по телефону"
}
→ ReservationDetailPayload
```

- `price: null` — вернуть расчётную цену ночи; ночь вне дат номера → `400`.
- `discountPercent` (0–100, `null` — без скидки) применяется к каждой ночи.
- Пересчитать сумму номера, брони и баланс.
- В историю (`logs`) — `action: "price_changed"`: старые и новые цены по
  датам, скидка, причина, сотрудник. `reason` обязателен.
- В `ReservationNightPayload`: `basePrice` (расчётная) **уже приходит**,
  добавить `discount` (сумма скидки ночи) и `isManual`. Фронт покажет
  «изменено вручную» и «вернуть расчётную».

### Своя сумма при создании и изменении

В `ReservationItemInput` (создание) и `ItemUpdatePayload` — необязательное
поле `manualTotal: Money`, сумма за весь номер. Бэкенд раскладывает её по
ночам поровну (остаток — на последнюю ночь), помечает ночи `isManual` и пишет
в историю. Без поля — как сейчас.

Новое право `hotel.prices.override` (суперадмину, как всегда, право не нужно).

**Сейчас на фронте (демо).**

- `PATCH …/pricing/` отвечает `404`, поэтому правка цен сохраняется на
  устройстве (`localStorage["mamadoc:hotel-demo:prices"]`). В «Проживании» у
  ночей пометка «вручную · демо», а рядом — сумма на сервере.
- Своя сумма при создании брони сервером сейчас молча игнорируется. Фронт это
  замечает (в ночах нет `isManual`, сумма не совпала) и тоже хранит её в
  демо-режиме.

**Признак:** в ночах брони приходит `isManual` — фронт включится сам. Цены из
демо-режима на сервер не переносятся: такие брони видны по пометке «демо», их
надо поправить заново.

## 5. Валюты: курсы объекта и оплата в валюте

Гости платят долларами, евро, рублями, тенге. Нужны курсы объекта и
`currency` в оплате. Показ сумм в другой валюте («режим валют») фронт делает
сам по этим курсам.

```http
GET /api/v2/hotel/properties/{id}/exchange-rates/        # hotel.view
PUT /api/v2/hotel/properties/{id}/exchange-rates/        # hotel.payments.manage
```

```json
{
  "baseCurrency": "KGS",
  "rates": [
    { "currency": "USD", "rate": "87.45", "updatedAt": "2026-10-02T09:10:00+06:00", "updatedByName": "Биймырза" },
    { "currency": "EUR", "rate": "101.20", "updatedAt": "…", "updatedByName": "…" }
  ]
}
```

`rate` — сколько базовой валюты за 1 единицу. `PUT` принимает
`{ "rates": [{ "currency": "USD", "rate": "87.50" }] }`; валюты, которых нет в
списке, удаляются.

Оплата (`POST /reservations/{id}/payments/`) — новые необязательные поля:

```json
{ "method": "cash", "amount": "50.00", "currency": "USD", "exchangeRate": "87.50", "kind": "payment" }
```

- Без `currency` — как сейчас (базовая валюта).
- `exchangeRate` не передан — текущий курс объекта; нет курса → `400`.
- В оплате хранить `amount` + `currency` (что дал гость) и `amountBase` (в
  валюте объекта); баланс брони считается по `amountBase`.
- В `PaymentPayload` добавить `amountBase`, `exchangeRate`, `baseCurrency`.
- Реестр кассы: группы `totals` уже «способ × валюта» — так и оставить
  (наличные доллары лежат в кассе отдельно), плюс `netBase` в каждой группе.
- Возврат — в той же валюте, по курсу на момент возврата.

**Сейчас на фронте (демо).**

- Курсы хранятся на устройстве (`localStorage["mamadoc:hotel-demo:rates:{propertyId}"]`);
  по умолчанию USD 87.45, EUR 101.20, RUB 1.05, KZT 0.18, правятся в
  настройках объекта.
- Оплата валютой записывается **обычной оплатой в сомах** (`amount` = сумма ×
  курс), а исходная сумма и курс — в начале `note`: `[USD 50 × 87.45] …`.
- Отчёт смены показывает «в т. ч. валютой» по этой пометке.

**Признак:** `GET /exchange-rates/` не `404` — фронт включится сам. Если у
объекта на сервере курсов ещё нет, форма подставит курсы с устройства и
попросит нажать «Сохранить».

**Миграция (по желанию).** Оплаты, внесённые в демо-режиме, можно перевести в
настоящие валютные: `note` совпадает с `^\[([A-Z]{3}) ([\d.]+) × ([\d.]+)\] ?`
→ `currency` = группа 1, `amount` = группа 2, `exchangeRate` = группа 3,
`amountBase` = нынешний `amount`, а пометку из `note` убрать.

## 7. Шахматка: долг и подробности брони прямо в календаре

Заказчик: в шахматке должно помещаться как можно больше, а при наведении на
гостя — больше данных, **особенно задолженность**. Фронт это уже показывает.
Но календарь (`GET /hotel/calendar/`) не отдаёт оплаты и подробности, поэтому
шахматка на каждую прокрутку догружает список броней за видимые даты (до
5 × 200 строк).

В `CalendarItemPayload` добавить:

| Поле | Тип | Откуда |
| --- | --- | --- |
| `paidAmount`, `balanceDue`, `currency` | Money, Money, string | бронь (одинаковые у всех позиций брони) |
| `customerPhone` | string | телефон заказчика (или основного гостя) |
| `externalId` | string | номер брони канала |
| `adults`, `children` | int | позиция |
| `ratePlanName` | string \| null | позиция |
| `guaranteeMethod` | string | бронь |
| `corporateName` | string \| null | бронь |
| `createdAt`, `createdByName` | ISO, string | бронь |
| `checkedInAt`, `checkedOutAt` | ISO \| null | позиция — фактическое время заезда и выезда |
| `internalNote`, `guestComment` | string | бронь |

**Признак:** если в позициях есть `balanceDue`, долг берётся из календаря.
Если там же `customerPhone`, список броней шахматка больше не запрашивает
вообще. Оба варианта фронт уже умеет и включит сам.

## 8. Массовое изменение цен одним запросом

Заказчик: «слева месяцы — нажал на месяц, выделил, и разом поменял цены для
всех номеров». Фронт сделал календарь цен на год (месяцы × категории × дни),
выделение месяцем, категорией или протяжкой, и панель массового изменения:
своя цена, ±%, ±сом, «авто», стоп-продажа, минимум ночей, дни недели.

Сейчас каждый непрерывный диапазон каждой категории уходит отдельным
`PUT /rate-plans/{id}/daily-rates/`. «Пт–Вс всего ноября для 4 категорий» —
это 20 запросов, «выходные на год» — 208. Каждый запрос — отдельная строка
«Истории цен», и если один упадёт, изменение сохранится частично.

```http
PUT /api/v2/hotel/rate-plans/{ratePlanId}/daily-rates/batch/      # hotel.rates.manage
{
  "reason": "Ноябрь: выходные +15%",
  "changes": [
    { "roomTypeId": 20, "dateFrom": "2026-11-06", "dateTo": "2026-11-09", "price": "3450.00" },
    { "roomTypeId": 21, "dateFrom": "2026-11-06", "dateTo": "2026-11-09", "stopSell": true, "minNights": 2 }
  ]
}
→ 200 { "nights": 120, "changes": 20 }
```

- Элемент `changes[]` — тот же объект, что принимает
  `PUT …/daily-rates/` сейчас: `dateTo` не включается; поля `price`,
  `clearPrice`, `stopSell`, `closedToArrival`, `closedToDeparture`,
  `minNights`, `clearMinNights`, `maxNights`, `clearMaxNights`; свой `reason`
  у элемента необязателен.
- Атомарно, одной транзакцией. Любая ошибка → `400` с
  `details.fields["changes[3].price"]`, и ничего не сохраняется.
- Лимит — до 2000 элементов, даты в пределах 400 дней.
- История — **одна строка**:
  - `kind: "daily_rate_batch"`, `roomTypeId: null`;
  - `dateFrom` и `dateTo` — самая ранняя и самая поздняя дата;
  - `reason`;
  - `changes: { "nights": 120, "items": [ …changes как прислали… ] }`.

  Фронт уже рисует такую строку («Массовое изменение цен»).

**Признак:** `…/daily-rates/batch/` не `404` — фронт включится сам. Пока
`404` — диапазоны уходят по одному, как сейчас.

Календарь цен (`GET /pricing/calendar/`) ограничен 62 днями, поэтому год —
это 6 параллельных запросов примерно по 0,6 с. Это терпимо. Поднять лимит до
366 дней — по желанию.

## 9. Отчёт «Доходность и загрузка»

Заказчик хочет видеть доходность и загрузку за период — и итогом, и **по
каждому дню** (как в Exely). Фронт сделал:

- группировку по дням, неделям и месяцам;
- детализацию по категориям, фильтры категорий и каналов;
- сравнение с прошлым периодом и с прошлым годом;
- таблицу, график, тепловой календарь загрузки и средние по дням недели;
- выгрузку в Excel.

Сейчас всё считается по всем броням периода. Год — это много страниц списка
броней, и выше 5000 броней отчёт честно пишет «посчитаны не все».

```http
GET /api/v2/hotel/reports/yield/?propertyId=7&from=2026-10-01&to=2026-10-31     # как список броней: hotel.view
```

```json
{
  "propertyId": 7,
  "currency": "KGS",
  "from": "2026-10-01",
  "to": "2026-10-31",
  "roomTypes": [{ "roomTypeId": 20, "roomTypeName": "Twin без окна" }],
  "inventory": [{ "date": "2026-10-01", "roomTypeId": 20, "available": 3 }],
  "sales": [{ "date": "2026-10-01", "roomTypeId": 20, "source": "booking", "sold": 2, "revenue": "3600.00", "roomsArrived": 1, "guestsArrived": 2 }]
}
```

Чтобы цифры совпали с тем, что фронт показывает сейчас:

- `from`, `to` — обе даты включительно, период ≤ 366 дней.
- В `sales` идут только брони со статусом `confirmed` (включая проживающих и
  выехавших) и только действующие позиции (`isActive`). Отменённые, неявки,
  черновики и холды не входят.
- `sold` — количество ночей позиций с этой датой.
- `revenue` — Σ (`price` − `discount`) этих ночей: только проживание, без
  допуслуг, в валюте объекта.
- `roomsArrived` — позиции с `checkIn` = дата; `guestsArrived` — сумма
  `adults + children` этих позиций.
- `source` — источник брони; пустой → `"other"`. `sales` — одна строка на
  (дата, категория, источник), только ненулевые строки.
- `inventory` — строка на каждую дату × категорию, даже если продаж нет.
  `available` — номера категории в продаже **на эту дату**: действующие
  (`status ≠ out_of_service`) минус блоки «снят с продажи / ремонт», которые
  покрывают дату. Фронт сейчас умеет учитывать только текущий статус номера —
  сервер посчитает точнее.

Сводку (недели, месяцы, итоги, ADR = доход / продано, RevPAR = доход /
доступно, загрузка = продано / доступно × 100, дни недели, сравнения) фронт
считает сам по этим строкам.

**Признак:** `/reports/yield/` не `404` — фронт включится сам. Отчёт сделает
один запрос вместо страниц броней.

## 10. Отчёт «Заезды»: фильтры, телефон, время заезда

«Заезды» (как `reservationsBalance` в Exely) — отчёт, которым пользуются
чаще всего. Фронт сделал колонки как в Exely с выбором «Вид», фильтры, печать
и Excel. Но брони берутся пересечением периода (до 2000), а по дате заезда
фронт режет их у себя.

1. `GET /reservations/?checkInFrom=…&checkInTo=…` (обе даты включительно),
   вместе с текущими фильтрами. Сейчас параметр игнорируется — проверено
   02.10.2026.
2. Там же фильтры `corporateAccountId=` и `balance=debt|overpaid|settled`
   (`balanceDue > 0`, `< 0`, `= 0`).
3. В списке броней — `customerPhone`. Сейчас фронт берёт телефон основного
   гостя позиции, и у брони без гостей телефон пустой.
4. По желанию: `expectedArrivalTime: "HH:MM" | null` — время заезда со слов
   гостя (в Exely в «Заездах» оно есть). Нужно в создании, `PATCH` и списке.
   Фронт покажет его вместо времени заезда объекта.

После выката фронт переключит запрос — это небольшая доработка.

## 11. Уборка: закрытые задачи, связь с бронью, отчёт по горничным

1. `GET /housekeeping-tasks/` при `status=done|cancelled` отдаёт **все**
   закрытые задачи без ограничений. Для отчётов нужны `completedFrom`,
   `completedTo` и пагинация `limit/offset` → `{ count, results }`. Старый
   ответ-массив можно оставить, когда `limit` не передан.
2. В `HousekeepingTaskPayload` — `completedById`, `completedByName`,
   `startedAt`; в создание — `reservationItemId`.

   Проверка номера перед выездом (сделана на фронте) сейчас хранит номер брони
   и результат в `note`. Задачу она держит «в работе» до выселения, потому что
   закрытую задачу потом не найти. С `reservationItemId` и фильтром
   `reservationItemId=` в списке фронт переделает это на нормальную связь.
3. Отчёт по горничным:
   `GET /api/v2/hotel/reports/housekeeping/?propertyId=7&from=…&to=…` → по
   сотрудникам: выполнено задач по видам, среднее время от `startedAt` до
   `completedAt`, разбивка по дням. Сейчас фронт считает нагрузку по броням и
   графику, а не по отметкам «убрано».

## 15. Согласие гостя на хранение и обработку персональных данных

Руководитель попросил, чтобы перед распознаванием паспорта была галочка о
согласии, а сам текст можно было менять «через админку или что-то подобное».

**Сейчас на фронте.**

- В «Новой брони» и «Новом госте» над фото паспорта — «Гость согласен на
  хранение и обработку персональных данных» со ссылкой на текст. Пока галочки
  нет, фото не прикрепляется и не уходит на распознавание: сначала
  открывается текст, «Гость согласен — продолжить» — и загрузка идёт дальше.
- В окне с текстом — «Печать»: бланк на подпись гостю (ФИО, подпись, дата).
- Текст правится в «Настройки → Объект → Согласие на обработку персональных
  данных». Каждое сохранение — новая редакция (`1.0` → `1.1`), чтобы было
  видно, на какой редакции гость согласился. Подстановки — `{отель}`,
  `{юрлицо}`, `{адрес}` (фронт берёт их из объекта и реквизитов §6).
- Стандартный шаблон (редакция `1.0`) — по Закону КР «Об информации
  персонального характера» от 14.04.2008 № 58; текст — в
  `src/dev/hotelConsent.ts` (`DEFAULT_CONSENT`). Перед боевым запуском его
  должен посмотреть юрист.
- Демо: своя редакция хранится на устройстве
  (`localStorage["mamadoc:hotel-demo:consent:{propertyId}"]`).
- В бронь уже уходит `dataConsent` (поле есть) и **новое** `dataConsentVersion`;
  в гостя — `dataConsent` и `dataConsentVersion`. Сервер их пока молча
  пропускает (проверено 02.10.2026).

### Текст согласия объекта

```http
GET /api/v2/hotel/properties/{id}/consent-template/      # hotel.view
PUT /api/v2/hotel/properties/{id}/consent-template/      # hotel.manage
```

```json
{ "title": "Согласие на хранение и обработку персональных данных", "body": "Я, гость отеля «{отель}»…", "version": "1.3", "updatedAt": "2026-10-02T21:40:00+06:00", "updatedByName": "Биймырза" }
```

- Пока своей редакции нет — `200` с `title: null, body: null, version: null`:
  фронт показывает свой стандартный шаблон (редакция `1.0`).
- `PUT { "title": "…", "body": "…" }` — новая редакция. `version` ведёт
  сервер: `1.1`, `1.2`…; `PUT { "title": null, "body": null }` — вернуть
  стандартный шаблон, но тоже с новой версией.
- **Старые редакции не удалять** — хранить историю (`ConsentTemplateVersion`:
  объект, версия, title, body, кто и когда). По `dataConsentVersion` из брони
  должно быть можно поднять ровно тот текст, который видел гость.
- Подстановки `{отель}`, `{юрлицо}`, `{адрес}` сервер хранит как есть, не
  раскрывает.
- «Через админку»: зарегистрировать модель в Django admin (только чтение
  истории + правка текущей редакции) — для поддержки; основное место правки —
  настройки объекта в CRM.

### Отметка согласия в брони и у гостя

1. Бронь: `dataConsent` уже есть. Добавить в создание и `PATCH` —
   `dataConsentVersion: string`; в `ReservationDetailPayload` —
   `dataConsentVersion`, `dataConsentAt` (время сервера, когда стало `true`),
   `dataConsentByName`. Смена `dataConsent` — строка в `logs`.
2. Гость (`POST/PATCH /hotel/guests/`): сейчас там только `marketingConsent`.
   Добавить `dataConsent: boolean`, `dataConsentVersion`, а в
   `GuestPayload` — ещё `dataConsentAt`. Согласие действует, пока не отозвано:
   отзыв — `dataConsent: false` (в историю гостя).
3. По желанию: `POST /guests/scan-document/` без согласия не обрабатывать —
   принимать поле формы `consent=true`, иначе `400 CONSENT_REQUIRED`. Фронт и
   так не шлёт фото без галочки, это страховка на сервере.

**Признак:** `GET …/consent-template/` не `404` — фронт включится сам. Если на
сервере своей редакции ещё нет, а на устройстве есть демо-редакция, настройки
подставят её и попросят нажать «Сохранить текст».

## 16. Распознавание паспорта на тесте: `503` только через 29 секунд

`POST /api/v2/hotel/guests/scan-document/` на `test.crm.operator.kg` отвечает
`503 RECOGNITION_UNAVAILABLE` через **~29 секунд** (02.10.2026, trace
`9a1fd3c6-487e-41b2-b2a2-048784973e98`) — провайдер распознавания не настроен
на стенде.

1. Настроить провайдер на тесте — иначе руководитель не увидит, как форма
   заполняется по фото.
2. Если провайдер не настроен (нет ключа) — отвечать `503` **сразу**, а не
   после таймаута: ресепшен все эти 29 секунд ждёт.
3. ID-карта резидента: фронт теперь запускает распознавание, только когда
   загружены **обе** стороны, но отправляет одну лицевую (`file`). Хорошо бы
   принимать и оборотную — поле формы `backFile` (на ней MRZ, ПИН и адрес
   прописки) — и читать обе за один запрос. Пока поля нет, фронт его не шлёт.

Фронт уже готов: пока идёт запрос — анимация «сканера», после первого `503`
распознавание до перезагрузки страницы не предлагается, поля заполняются
вручную.
